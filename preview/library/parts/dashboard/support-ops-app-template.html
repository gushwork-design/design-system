Dashboard templates

Whole pages, built from the components, to copy and fill in rather than rebuild. A template is not a component and nothing in it is new: it proves the components compose and gives a builder a verified starting point. Web templates live in skills/gushwork-web/templates/; dashboard templates live in skills/gushwork-dashboard/templates/.

Analytics overview template

Purpose. A Monitor-and-explore screen: how a thing performed over a period, against the previous period, broken down and listed. Use it as the start for an overview, a campaign report or a weekly readout. Do not use it for a settings page, a detail page or an explorer with a query panel; those follow the other recipes in patterns.md.

Files. skills/gushwork-dashboard/templates/analytics-overview/analytics-overview.html, one static file linking foundation/tokens.css, exports/dashboard/dashboard.css and dashboard.js. A generated copy sits in templates/analytics-overview/ (links re-based for that depth, with a README), and another is served to the review drawer at /previews/dashboard/pages/analytics-overview.html, with its links made absolute and the stamp's registry URL blanked so the build notice stays quiet while it is being reviewed; it is regenerated by scripts/build-dashboard-css.sh, never edited.

Archived (5 Oct 2026). Not listed on the hub's Templates page or in the Design System library for now: the card, the live preview route, the library entry and the access entry are removed. The files stay (the skill's template, its copy in templates/analytics-overview/, the review drawer's copy) so it can be listed again.

How to use. Copy the folder to the new project and edit the copy. Do not reference another built dashboard. Replace the sample copy and figures, keep the Sample data Badge until real data replaces them, change the stamp's components list to exactly what the page uses, and delete what the screen does not need. Every figure in it is invented.

What it contains, in order. app-shell with a grouped sidebar, account-row and theme-menu → page-header (title, Sample data Badge, a comfortable and compact density switch, Export) → tabs-underline → time-range-bar (range, granularity, comparison) → four stat-cards with delta-pills and sparklines → chart-frame with a line-chart (this period against the previous one) → horizontal-bar-chart by channel → funnel → data-table with table-toolbar, saved-views, filter-builder, column-menu, row-selection, sortable columns and pagination → bulk-action-bar → toast from Export → confirm-dialog from Remove. The build stamp lists the components used.

Verified. Light and dark; comfortable and compact; 1440, 1280 and 390 wide; one scroll region with the rail fixed; no console errors; Export raises a toast; selecting a row raises the bulk bar; a column sorts; Remove opens a confirm dialog that names what is lost, focuses Cancel and returns focus to Remove.

Tokens. None of its own. Everything comes from the components it uses.

Provenance. NEW, pending library review. It is deliberately not listed on the hub's public Templates page yet: adding its card there is the step that makes it live, and it waits for a pass.

Support operations app template

Purpose. A whole multi-page product app to copy and fill in: nine pages behind one flat rail, with underline tabs for the views inside a page, on one set of sample data. Use it as the start for any app that has lists of things, a page per thing, reports, a team and settings. Use analytics-overview instead when the job is one report page. The sample is a support desk (tickets, queues, agents, customers, help articles) because it exercises every status and priority the components can show; the structure is not specific to support.

Files. skills/gushwork-dashboard/templates/support-ops-app/, static HTML with no build step, each page linking foundation/tokens.css, exports/dashboard/dashboard.css and dashboard.js:

The rail and the tabs. The rail is flat, as on the design hub: three labelled groups, one row per page, no submenus. The views inside a page are tabs-underline in its header (gd-page-header__tabs). A tab changes the view in place and keeps the address in step (reports.html?report=response), so a reload or a shared link lands on the same view; app.js bindTabs does this. Tickets' views carry their counts in the tabs. The Help center's articles keep saved-views, a second row of counted filters under the page's one underlined row (R59), and Settings keeps its own sub-nav because that is the component for a settings area. The rail, topbar and account row are the same markup on every page, so a change to them is made in every file.

How to use. Copy the folder to the new project and edit the copy. Do not reference another built dashboard. Re-point the three links at your copy of the tokens and the dashboard set. Replace data.js and the handlers that say "Nothing is stored" with calls to your own API. Keep the Sample data Badge until real data replaces the sample, set each page's build stamp components list to exactly what it uses, and delete the pages you do not need together with their rail rows (a rail row that goes nowhere is a dead control).

What the pages are made of.

  • Overview. page-header with the density switch and Export → time-range-bar (a plain container, not the sticky filter slot, so it scrolls with the page) → four stat-cards with

delta-pills and sparklines → line-chart → horizontal-bar-chart → breakdown-bar → a data-table of what needs attention.

  • Reports. tabs-underline for the three reports → period-select (also a plain container, not sticky) → four stat-cards with delta-pills → a bar-chart or line-chart (with a target line on

Response times) → a horizontal-bar-chart or breakdown-bar → a data-table with progress-bar cells.

  • Explorer. explorer-layout in a data-fill panel body → period-select → query-builder → a chart → a results table. Editing

the query marks the result out of date; Run query redraws. More than three groups fold into Other.

  • Tickets. tabs-underline for the views, with counts (the toolbar and table sit on the page itself, the table's own frame being the only container, with no outer card) → table-toolbar (search, filter-builder, column-menu, Export) → filter-chips →

data-table with row-selection, row-actions-menu → pagination → bulk-action-bar → table-states → drawer → modal with form-field errors → confirm-dialog.

  • Ticket. breadcrumbs, a small page-header with a status Badge, a menu and one primary action → tabs-underline → a reply

card → activity-timeline → key-value-list → a progress-bar against the first response target → Resolve with an Undo toast.

  • Customers. Four stat-cards → a card holding a table-toolbar, a data-table with Badge and person cells, and pagination.
  • Help center. Four stat-cards → saved-views → a data-table with row-actions-menu (publish, copy, delete) → a new-article

modal; Categories adds a horizontal-bar-chart.

  • Team. Four stat-cards → a data-table of agents with status Badges and progress-bar cells; Workload adds a

horizontal-bar-chart and a breakdown-bar.

  • Settings. sub-nav switching sections by the address hash → form-sections of form-fields and setting-rows with

toggles → one unsaved-changes-bar → a members data-table, an invite modal and a confirm-dialog.

Density. Comfortable by default (R57). The Comfortable and Compact switch is in the page header so a reviewer can see both; the choice is kept across pages in localStorage. Remove the switch when the product does not offer one.

Verified. Light and dark; comfortable and compact; 1440, 1280 and 390 wide, including the rail as a phone drawer; fifteen page views checked for the right rail row current and the right tab selected, no horizontal overflow, no unlabelled button and no console error; every data-gd-emit has a handler; list views, search, filters, bulk actions, drawers (focus returns), dialogs with field errors, publish, delete and Resolve with Undo work; the Explorer runs, filters and folds; a Settings change raises the save bar and Save clears it.

Layout figures chosen here, not documented. The explorer's query pane is 360 wide and its chart pane 440 tall (the query builder's 112px label column needs about that width); the Ticket and Settings pages stack their columns with an inline display:flex; gap:var(--gd-gap) because the set has no stack component, and a row of stat cards that a script fills sits in a nested gd-grid with padding:0; the tickets table's minimum width is 1040.

Not in this template. A loading skeleton for each page (the state matrix in patterns.md still applies when real data is asynchronous), a command palette behind the search trigger, a company or person detail page, and sign-in.

Tokens. None of its own. Everything comes from the components it uses.

Provenance. NEW, pending library review (R43), registered as support-ops-app-template. Listed on the hub's Templates page under Dashboard, with a live preview at /internal/templates/support-ops-app (the same files the review drawer shows).
