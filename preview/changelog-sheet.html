2aaed30 Can AI find your business — lead magnet PDF
v1.42.0 28 Aug 2026 14:04

the unavailable state, and a doc that pointed at nothing

Two findings from a teammate building a dashboard over five separate stores.

Full notes

1. There was no ruling for "we could not read this". states.md ruled empty and loading on 7 Aug and stopped there, but failed is a third condition, not a shade of either: empty means we read the source and it held nothing; unavailable means we could not read it at all. With five stores behind one page, any one can fail while the others are fine, so the state belongs to the card that failed rather than to the page.

The ruling is one line — an element that encodes a quantity is REMOVED, never zeroed. A progress bar at 0%, a percentage of 0%, a sub-line of "of 0" and a value of "—" are all measurements; they say "we looked, and the answer is nothing", which is a different claim from "we could not look" and is the one a reader acts on.

The principle was already half-ruled. The loading section says never render a 0 or a dash while data is in flight, because a 0 that means "not loaded" reads as "we got no leads". What was missing was its scope, not its reasoning. R10 points the same way for toasts.

Scope is any data-bearing card or section, ruled ahead of Figma as the rest of states.md already is. The card keeps its surface, radius, padding, label and footprint so the page does not change shape when a store goes down; only the parts carrying a quantity change. No new token of any kind — status-dot Status=behind, Badge Color=Red, and the value dropping to body-14-med on neutral-500 are all existing variants. The proposal specified Badge Tone=danger; Badge has no Tone property, and the correction is recorded.

2. output-targets.md told every build to import from components/dashboard/ before writing a component. That folder does not exist and never did — there is not one .tsx or .jsx in the plugin — so anyone following the instruction hit a wall. It now points at the measured specs in exports/, which is what the folder would have been compiled from. Whether to build it for real is a separate decision and is in the backlog, not settled here.

stat-card and metric-card bump to 1.42.0, breaking: false — existing builds render correctly, they simply have no failure treatment, so owners get the amber notice rather than the red one. metric-card's existing card-layout FINDING is preserved alongside the new note. kpi-card and analytics-card are in scope for the ruling but are v1 section-elements and absent from the registry, so nothing was bumped there.

the plugin loads again: drop the duplicate hooks declaration

v1.41.0 shipped hooks/hooks.json AND declared it in the manifest. Claude Code loads hooks/hooks.json from the standard path unconditionally, then checks each manifest.hooks entry against what it has already loaded — so that declaration could only ever collide with itself:

Full notes

Hook load failed: Duplicate hooks file detected: ./hooks/hooks.json resolves to already-loaded file .../gushwork-design/1.41.0/hooks/hooks.json

The whole plugin fails to load, not just the hook — both skills go with it. So the one release whose headline was "updates that find you" is the release that silently takes the design system away from anyone who installs it. Anyone already running autoUpdate got it at their next start; the hook meant to turn autoUpdate on for everyone else cannot run, because it lives inside the plugin that no longer loads.

The fix is to delete the key. hooks/hooks.json does not move and is not renamed — it loads from the standard path, which is where it already was. manifest.hooks is only for ADDITIONAL hook files. check-update.test.sh still passes 13/13.

Bumped rather than corrected in place on 1.41.0: the cache is keyed by version (~/.claude/plugins/cache/<marketplace>/<plugin>/<version>/) and version is the field plugin update compares, so a fix that does not move it does not reach a machine already holding a broken 1.41.0.

One thing to carry into the next release: claude plugin validate . does NOT catch this. It finds .claude-plugin/marketplace.json first, validates the marketplace manifest and returns before any plugin-level check runs — it passes cleanly on the broken 1.41.0. Step 5 of the release flow in CONTRIBUTING.md cannot be trusted for plugin-manifest errors. claude plugin list reading "enabled" after an install is the check that would have caught it in seconds.

3d44b20 Gushwork design plugin fails to load
v1.41.0 26 Aug 2026 13:20

updates that find you, a public version manifest, and a one-line install

Three gaps that were documented but had no code behind them.

Full notes

1. A SessionStart hook, shipped inside the plugin (hooks/hooks.json -> scripts/check-update.sh). ROLLOUT.md said autoUpdate is per-machine, unsettable from repo settings, so "either your MDM payload writes it, or people run this once" — and a skipped flag means emitting last month's colours with full confidence. The hook arrives with the plugin, so it runs whether or not anyone flipped anything: it sets the flag once, and names the components that changed and which are breaking for a screen built on the old ones. It also closes the other half of that gap — auto-update lands a version but takes effect only on the NEXT start, so the session that could warn you is the one that did not know.

It is silent when there is nothing to say, capped at a 10s hook timeout with a 3s fetch and a 6h cache, and every failure path exits 0. check-drift.sh said push was impossible for a git-clone plugin; a pull at session start is the closest honest thing, and it needs no stamp in the file.

2. version.json, generated at publish time by scripts/version-json.sh and served from the root of the deploy. Never committed — it is a projection of marketplace.json and component-registry.json, so a committed copy could only be a second thing to go stale. The hook reads it over HTTPS and falls back to a git fetch in the marketplace clone. Reading a public URL is the point: the thing that tells you that you are behind must not require the access that being behind might have cost you. Same reasoning that already puts component-registry.json on that deploy.

3. One-line install. scripts/install.sh already did all three steps idempotently; nothing pointed at it. It now leads INSTALL.md, ROLLOUT.md and the install page, and the raw python one-liner that hand-edited known_marketplaces.json is gone from both routes — the hook does that now. The page gains a "Staying current" section, reusing existing classes and no new tokens.

Also repairs a live skew: v1.40.0 moved plugin.json and both SKILL.md announce lines but not marketplace.json or preview/install.html, because stamp-release.sh was never run for it. The marketplace advertised 1.39.0 for ten days and the live install page told readers that anything below 1.39.0 was stale. publish-sheets.sh now refuses to deploy when those version fields disagree, which is the gate that would have caught it.

scripts/check-update.test.sh covers the hook: 13 assertions over behind/current/ ahead, breaking-component reporting, malformed payloads, a missing plugin root, a dead endpoint under a time cap, and the autoUpdate flip being idempotent and refusing an unparseable config. It caught two real bugs on the first pass — an ERR trap that swallowed the git fallback, and a backgrounded timeout that held stdout open for the full timeout on every capped call.
